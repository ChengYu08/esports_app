# 星钻充值支付接入方案

> 调研日期：2026-10-15  
> 适用项目：盼之电竞移动端（Expo / React Native）  
> 文档状态：技术调研与接入基线，尚未接入支付 SDK

## 结论

支付需要按应用分发渠道拆分，不能用一个社区插件同时解决所有商店内购和中国大陆钱包支付。

- iOS App Store 版本使用 Apple IAP。项目需求已经指定使用 Apple IAP 和 App Store Server Notifications V2。
- Google Play 版本的应用内星钻购买使用 Google Play Billing。Expo 项目优先评估 `expo-iap`，它统一封装 Apple StoreKit 和 Google Play Billing。
- 中国大陆第三方 Android 应用市场版本可按渠道要求接入微信支付、支付宝 App 支付。它们需要独立的原生支付桥接和服务端回调验签。
- Android 微信、支付宝和 iOS / Google Play IAP 是不同支付通道。订单、余额和星钻流水可以由业务后端统一管理，付款凭证、验签和退款处理必须按通道实现。

## 项目现状与既有要求

- 当前项目使用 Expo SDK `~57.0.24`、React Native `0.86.3`，并已安装 `expo-dev-client`。当前 `package.json` 未包含 IAP、微信支付或支付宝支付插件。
- [移动端项目需求文档](./盼之电竞1.0-移动端-项目需求文档.md) 已规定：所有平台使用服务端下发的充值档位；iOS 接 Apple IAP 和 App Store Server Notifications V2；Android 复用微信、支付宝支付拉起能力；支付结果以服务端订单状态为准。
- 现有代码已有 `POST /client/v1/pay/createPayOrder` 下单接口和星钻余额查询能力。当前下单接口返回二维码内容，接入手机端原生支付前需要确认或扩展响应，使 Android 原生 SDK 能拿到对应渠道的 App 支付参数。IAP 需要走商店商品和交易凭证校验流程，不能直接沿用二维码响应。
- 星钻充值 UI 已完成；充值按钮目前不代表支付链路已经接通。接入时应把 UI、商店商品、后端订单和余额刷新串起来。

## 社区插件评估

版本信息根据 npm 元数据和各仓库 README 查询，可能随时间变化。接入前应重新检查维护状态、Expo SDK 兼容性和原生构建要求。

| 插件 | 当前查询版本 | 能力与限制 | 建议 |
| --- | --- | --- | --- |
| [`expo-iap`](https://www.npmjs.com/package/expo-iap) | `6.0.2` | OpenIAP 的 Expo Module，统一支持 Apple StoreKit 和 Google Play Billing。需要开发构建才能进行真实购买，不能用 Expo Go 完成真实支付测试。 | **IAP 首选。** 按 SDK 57 对应文档核对安装、配置和测试流程后再接入。 |
| [`react-native-iap`](https://www.npmjs.com/package/react-native-iap) | `17.0.2` | 与 `expo-iap` 属于同一个 OpenIAP 项目，采用 Nitro Modules。该项目将 Expo 应用指向 `expo-iap`。 | 当前 Expo 项目优先使用 `expo-iap`，不同时引入两个 IAP 库。 |
| [`react-native-wechat-lib`](https://github.com/little-snow-fox/react-native-wechat-lib) | `1.1.27` | README 指出 iOS SDK 不含支付功能；3.x 仍处于开发阶段，部分功能未测试。 | 不能作为 iOS 和 Android 都可用的微信支付方案。Android 接入前需验证与 RN 0.86、Expo SDK 57 的兼容性。 |
| [`react-native-alipay-v5`](https://www.npmjs.com/package/react-native-alipay-v5) | `5.0.4` | README 提供 iOS、Android 支付宝原生桥接，但要求配置 URL Scheme 和 iOS AppDelegate 回调。README 未提供 Expo SDK 57 的即插即用配置。 | 可作为支付宝桥接候选；Expo CNG 项目需通过 config plugin 或本地 Expo Module 管理原生配置，并完成开发构建验证。 |
| [`react-native-purchases`](https://github.com/RevenueCat/react-native-purchases) | `10.13.0` | RevenueCat 提供 IAP 收据校验、商品和事件管理能力。它增加一项外部服务，交易和星钻入账仍需接入业务后端。 | 可作为后续减少商店交易运维工作的备选；目前已有自有订单后端，首期不必增加这一层。 |

目前没有找到一个同时适配 Expo、覆盖 iOS/Google Play IAP 和中国大陆微信/支付宝 App 支付，并且无需额外原生配置的单一社区插件。

## 建议的分平台方案

### iOS App Store

1. 在 App Store Connect 配置星钻消耗型商品 ID。商品价格以商店商品信息为准，星钻数量由服务端维护商品映射。
2. 客户端使用 `expo-iap` 加载商品并发起购买，不允许客户端自行传入金额或星钻数量来决定入账数量。
3. 客户端把交易凭证或 StoreKit 交易数据提交给业务后端；后端向 Apple 验证交易、校验商品与用户绑定，并以幂等方式写入星钻流水和余额。
4. 后端实现 App Store Server Notifications V2，处理交易状态变化、退款和撤销退款。根据现有项目需求，退款事件要触发已消费星钻的冲正或补偿处理。
5. 只有后端确认入账后，客户端才刷新余额并结束待完成交易。支付弹窗回调只用于更新界面，不能直接给用户加钻。

项目需求文档提出 iOS 档位按原价 7 折展示，并建议首发提供 2–3 个低价档位。最终价格和商品 ID 需要产品、服务端与 App Store Connect 使用同一份映射。

### Google Play

如果应用通过 Google Play 分发，星钻属于应用内数字商品，默认使用 Google Play Billing。使用 `expo-iap` 发起购买，由后端通过 Google Play Developer API 校验订单，再幂等发放星钻。仅在目标地区、账号和应用符合 Google Play 替代支付计划条件时，才考虑对应替代方案。

### 中国大陆 Android 应用市场

微信和支付宝走各自的 App 支付 SDK。建议将支付通道收敛在业务层 `PaymentProvider` 接口下，由渠道配置决定是否显示微信或支付宝选项。

推荐流程：

1. 客户端向后端请求创建充值订单，只传商品档位 ID 和支付渠道。
2. 后端根据商品配置计算价格、星钻数量和业务订单号，调用支付平台下单，并返回 App SDK 所需参数。
3. 客户端使用原生桥接拉起钱包应用。成功、取消或处理中等客户端返回状态仅用于界面提示。
4. 支付平台异步通知业务后端。后端验签并确认金额、商户订单号和支付状态后，更新订单并写入星钻流水。
5. 客户端通过查询订单状态或刷新余额确认最终结果，处理用户从钱包返回时回调丢失或状态仍在处理中的情况。

目前 `createPayOrder` 返回二维码内容。手机端通过支付宝或微信 App 支付时，后端需返回对应 App SDK 的参数；只有适用于网页或另一台设备扫码的流程才应展示二维码。

## 后端接口与账务要求

实施前需让移动端、业务后端和支付后端确认以下契约：

- 服务端商品目录：商品 ID、商店 Product ID、人民币价格、星钻数量、可用平台和上下架状态。
- 创建充值订单：客户端只提交商品 ID、平台和支付渠道；服务端计算应付金额和星钻数量。
- IAP 交易验证：接受 Apple / Google 交易凭证，绑定当前登录用户和订单，返回服务端最终订单状态。
- 微信 / 支付宝下单：返回客户端 SDK 参数，而非只返回二维码文本。
- 订单查询：客户端恢复前台或从支付应用返回时可查询处理中订单。
- 支付平台回调：验签、核对商户订单、金额、币种和交易状态后才能入账。
- 交易流水与幂等：以平台交易 ID、商户订单号等建立唯一约束，重复客户端请求或重复通知均不能重复发钻。
- 退款和冲正：保存余额变更原因、关联支付交易与冲正记录，确保退款通知重复到达时仍然幂等。

客户端支付成功回调、二维码扫描结果和本地缓存余额都不是资金入账的事实来源。服务端订单状态和星钻账本是唯一事实来源；签名私钥、商户密钥和 App Store Server API 私钥不得放在客户端。

## Expo 接入注意事项

- 添加或升级 Expo 原生模块前，应查阅 [Expo SDK 57 文档](https://docs.expo.dev/versions/v57.0.0/)，并使用 Expo 推荐的安装方式核对依赖版本。
- `expo-iap`、微信和支付宝原生 SDK 均不能只靠 Expo Go 验证真实支付。使用 EAS 或 `expo run:ios` / `expo run:android` 构建包含原生依赖的开发版本。
- 项目采用 Expo Continuous Native Generation。不要手工修改生成的 `ios/` 和 `android/` 目录；需要的 URL Scheme、回调处理、Gradle 或 iOS 配置应由维护的 config plugin 或本地 Expo Module 注入。
- 每个支付通道都要在真实设备和支付沙箱 / 测试商户环境中验证，特别是钱包未安装、取消支付、支付处理中、回跳失败、重复通知、退款及应用进程被系统回收等场景。

## 商店规则边界

Apple App Review Guidelines 3.1.1 通常要求通过 IAP 销售应用内数字内容和虚拟货币。指南 3.1.3(d) 对实时、两个人之间的一对一服务设有窄范围例外，但星钻是可在多个服务订单中使用的通用余额时，是否适用该例外不能仅凭业务名称判断。

当前项目需求已经明确选择 iOS IAP，应按此方案实现。若产品希望为一对一陪玩服务改用站外付款，应先按实际消费流程确认 App Review 适用规则，不要先在 iOS 客户端开放微信或支付宝充值。

Google Play 分发版本应按 Google Play Payments policy 使用 Play Billing；中国大陆其他安卓应用市场不等同于 Google Play，需逐个确认分发渠道的支付和上架要求。

## 建议实施顺序

1. 产品、服务端与移动端确认充值档位、IAP 商品 ID、Android 分发渠道和退款冲正规则。
2. 服务端补全商品目录、IAP 验证、订单查询、星钻账本幂等和 Apple Server Notifications V2 处理。
3. 移动端接入 `expo-iap`，通过 Apple / Google 沙箱验证购买、取消、挂起、恢复、重复通知和退款流程。
4. 若首期包含中国大陆 Android 应用市场，再单独评估微信与支付宝桥接。支付宝先验证 `react-native-alipay-v5` 是否能通过本地 config plugin 在 Expo SDK 57 / RN 0.86 开发构建中稳定运行；微信支付需选定明确支持目标 Android SDK 的原生桥接方案，不能把 `react-native-wechat-lib` 当作 iOS 方案。
5. 在目标发行包中验证渠道隔离：App Store / Google Play 使用商店支付；其他 Android 包只展示该渠道允许的支付方式。
