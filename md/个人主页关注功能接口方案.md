# 个人主页关注功能接口方案

## 结论

当前 PC 端和后端均没有可供移动端直接调用的真实关注接口。PC 端的 `toggleFollow` 仅在本地反转 `following` 状态并展示提示；该按钮在页面模板中仍处于注释状态。后端 `UserFollowController` 当前只提供按关注关系主键查询详情的接口，不能用于关注、取消关注或判断当前用户是否已关注目标用户。

移动端个人主页已经有“关注”按钮，但点击事件为空。实现该功能前，需要先补齐由服务端作为唯一事实来源的关注关系接口。

## 现状

| 位置 | 当前行为 | 结论 |
| --- | --- | --- |
| PC 端 `pzdj-pc/pages/user/[id].vue` | `toggleFollow` 只执行 `following.value = !following.value`，不发起网络请求。 | 不能复用为移动端接口调用逻辑。 |
| 后端 `pzdj-service/.../UserFollowController.java` | 仅有 `GET /userFollow/detail?id={id}`。 | 缺少面向当前登录用户的关注关系操作接口。 |
| 移动端 `ProfileScreen.tsx` | 他人主页展示“关注”按钮，`onPress` 目前为空。 | 需要接入初始关系查询和变更操作。 |
| 移动端 `apiClient` | 支持通过 `token` 请求头传递 C 端业务 token。 | 新接口应沿用此鉴权方式。 |

## 建议接口契约

以下路径沿用移动端现有的 `/client/v1` API 约定。具体控制器路径可按后端项目规范调整，但请求语义和返回字段应保持一致。

### 查询关注状态

`GET /client/v1/user/follow/status?targetUserId={targetUserId}`

该接口根据当前登录用户和目标用户查询关系，用于个人主页首次渲染。

请求头：

```http
token: <当前登录用户的业务 token>
```

成功响应：

```json
{
  "success": true,
  "code": "SUCCESS",
  "info": "操作成功",
  "data": {
    "targetUserId": 50100028,
    "following": false
  }
}
```

### 关注用户

`POST /client/v1/user/follow`

请求体：

```json
{
  "targetUserId": 50100028
}
```

该操作必须幂等：重复请求同一目标用户时保持已关注状态，不重复创建关注记录，也不重复增加目标用户粉丝数。

成功响应：

```json
{
  "success": true,
  "code": "SUCCESS",
  "info": "操作成功",
  "data": {
    "targetUserId": 50100028,
    "following": true
  }
}
```

### 取消关注

`POST /client/v1/user/follow/cancel`

请求体：

```json
{
  "targetUserId": 50100028
}
```

该操作必须幂等：目标用户本来未被关注时仍返回成功，最终状态保持未关注。

成功响应：

```json
{
  "success": true,
  "code": "SUCCESS",
  "info": "操作成功",
  "data": {
    "targetUserId": 50100028,
    "following": false
  }
}
```

## 后端规则

1. 从认证上下文读取当前用户 ID，不能由客户端提交关注发起人 ID。
2. 拒绝关注自己、目标用户不存在等非法请求，并返回明确的业务错误。
3. 以当前用户 ID 和目标用户 ID 作为唯一关系；数据库应具备唯一约束或等价的并发保护。
4. 关注和取消关注应在同一事务内维护关注关系及目标用户的粉丝数快照。
5. 不要使用“切换关注状态”的单一接口。网络重试或重复点击会使 toggle 语义不可预测；分离的关注和取消关注接口可以保证幂等。

## 移动端接入方案

### 个人主页初始化

1. 仅在查看他人主页且用户已登录时，查询关注状态。
2. 未登录用户仍可浏览个人主页，按钮保持“关注”；不查询需要登录的关系接口。
3. 查询成功后根据 `following` 展示“关注”或“已关注”。

### 点击关注按钮

1. 未登录时进入现有登录流程，不请求关注接口。
2. 请求进行中禁用按钮，防止重复提交。
3. 当前为未关注状态时调用关注接口；当前为已关注状态时调用取消关注接口。
4. 仅在服务端返回成功后更新本地按钮状态，并显示“关注成功”或“已取消关注”。
5. 请求失败时保留原状态并展示服务端或网络错误信息。

### 数据层建议

在 `src/features/mine/api/` 新增独立的 follow contract/API 模块，并以 React Query 管理：

| 数据 | Query key | 用途 |
| --- | --- | --- |
| 当前用户对目标用户的关注关系 | `['user-follow-status', targetUserId]` | 个人主页初始化和缓存。 |
| 关注或取消关注 | mutation | 按接口结果更新上述缓存。 |

个人主页详情中的 `fansCount` 是目标用户的粉丝总数。若变更接口返回最新粉丝数，移动端可以同步更新详情缓存；若不返回，则在操作成功后使 `['profile-detail', clubId, userId]` 失效并重新拉取，以服务端数据为准。

## 测试范围

1. API contract 测试：验证状态查询、关注、取消关注的请求路径、请求体和成功映射。
2. 个人主页交互测试：未登录不发请求；关注成功后状态更新；失败后状态不改变；请求期间不能重复触发。
3. 后端接口测试：重复关注、重复取消关注、关注自己和目标用户不存在等场景。

## 实施前置条件

后端先提供上述三类接口并明确最终路径、鉴权上下文获取方式和错误码。移动端以最终接口文档为准完成 API 模块、React Query 状态和个人主页按钮接入。
